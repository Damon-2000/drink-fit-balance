# API Contracts

## 1. 文件目的

本文件定義 醉後比較 前端與後端之間的 API 契約，作為前端 API Client、Service、資料型別、Mock 資料及整合驗證的依據。

本文件主要描述：

- API 的用途與呼叫方式。
- Request 與 Response 的資料格式。
- 錯誤處理與非同步操作規則。
- 前端與後端的責任邊界。
- 尚待確認的 API 設計事項。

本文件不定義靜態資料檔與瀏覽器本地儲存的內部實作細節，也不取代產品功能規格。

本專案目前沒有後端，也沒有建立後端的計畫。§5 的 API 由專案內的靜態資料提供（Mock 模式恆開），契約的作用是固定資料格式，讓型別、靜態資料與畫面保持一致；日後若改由後端提供，前端不需要改變呼叫方式。

## 2. 相關文件

- `docs/spec/product-spec.md`：功能需求、業務規則與系統職責分工。

若 API 契約與產品規格存在衝突，應記錄問題並確認後再修改，不得自行選擇其中一方。

## 3. 使用與維護規則

### 3.1 契約狀態

每項 API 或共用資料結構都應標記以下其中一種狀態：

- `Proposed`：設計提案，尚未獲得相關開發方確認。
- `Confirmed`：前後端已確認契約內容。
- `Implemented`：已在指定系統中實作，並有實際驗證依據。
- `Deprecated`：已不建議使用，等待移除或替換。

`Confirmed` 不代表 API 已完成實作。

若前後端只有一方完成實作，不得將整合狀態視為已完成。

本專案只使用以上四種契約狀態。尚待決定的問題不另設狀態，一律列於 §8 Open Questions，並在相關契約的 Notes 中引用。

### 3.2 開發前的檢查

AI Agent 在新增或修改 API 整合前，應：

1. 閱讀本文件中與任務相關的契約。
2. 檢查現有 API Client、Service 與資料型別。
3. 確認契約狀態及相關限制。
4. 確認 Request、Response 與錯誤處理方式。
5. 若契約尚未確認，應先標示待確認事項，不得直接假設後端已具備該能力。

### 3.3 契約更新原則

- 新增 API 時，應先記錄用途、Method、Path、Request、Response 與錯誤處理方式。
- 契約有變動時，應同步檢查相關型別、Service、UI 與 Mock 資料。
- 不得只修改文件而忽略既有實作。
- 不得只修改程式碼而讓文件持續描述舊契約。
- 若 API 行為改變了產品需求，應同步檢視 `product-spec.md`。
- 尚未確認的內容應列為 Open Questions，不得混入已確認契約。
- Mock 資料僅供前端開發與驗證，不代表後端已實作該 API。

## 4. 共通 API 規範

以下內容均為初始設計提案，實際採用前須由前後端確認。

### 4.1 Base URL

API Base URL 由 `config/` 統一提供，不將不同環境的網址散落於程式碼中。

前端部署為 GitHub Pages 靜態網站（見 `frontend-architecture.md` §3.2），無法在同一個專案中實作後端。後端日後若存在，只能是獨立服務，並遵守本文件定義的 Path 與資料格式；前端只透過 Base URL 切換。

目前沒有後端，因此沒有正式環境的 API 網址。

### 4.2 資料格式

建議使用：

- HTTP API。
- JSON Request 與 Response。
- ISO 8601 格式的時間字串，並明確定義時區。
- 明確的錯誤代碼與錯誤訊息。
- 一致的 HTTP 狀態碼語意。

具體欄位與格式須依各 API 契約確認。

### 4.3 共通錯誤處理

建議錯誤回應格式：

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request validation failed",
    "details": {}
  }
}
```

此格式為提案，尚未確認為正式後端契約。

前端應依 HTTP 狀態碼及已確認的錯誤代碼處理錯誤，不應只依賴錯誤訊息文字進行程式判斷。

### 4.4 非同步操作

目前沒有寫入型 API：使用者資料、運動偏好與飲酒紀錄都只保存在瀏覽器本地（見 §4.6）。日後若新增寫入型 API（例如上傳飲酒紀錄），應區分：

- 請求是否已被接受。
- 後端或外部系統是否已執行操作。
- 實際狀態是否已更新。
- 操作是否失敗或逾時。

HTTP 請求成功不必然代表操作已實際完成。

若後端採非同步執行，應明確定義操作識別碼、結果查詢方式及逾時處理方式。

### 4.5 安全與資料驗證

- API Key、Token 與其他機密資訊不得提交至 Repo。
- 不得將伺服器憑證或機密值直接寫入前端程式碼。
- 前端表單驗證不能取代後端驗證。
- 會改變實際狀態或涉及安全規則的操作，必須由後端（及必要的外部系統）執行權限與資料驗證。
- 不得依賴瀏覽器執行需要可靠執行的判斷，例如安全、計時或計費。

### 4.6 前端本地設定

由於目前不存在後端，以下資料皆為純前端狀態，保存於瀏覽器 localStorage，不屬於本文件的 API 範圍，處理方式見 `frontend-architecture.md` §7：

- 使用者資料：身高、體重。
- 運動偏好：每項運動是否開啟。
- 飲酒紀錄：進行中的一輪與前一輪紀錄。

若未來需要將設定保存於後端，須先於本文件新增 `Proposed` 契約。

### 4.7 Mock 資料與契約

- 前端 Mock 資料必須符合本文件的 Request 與 Response 定義。
- 撰寫 Mock 資料前，若契約缺少所需欄位，應先在本文件以 `Proposed` 補上，再撰寫型別與 Mock 資料。
- Mock 資料能讓前端運作，不代表契約已被後端確認，契約狀態不得因此提升。

## 6. 共用資料結構

本節先列出前端預期使用的資料概念，實際 JSON Schema 尚待確認。

`product-spec.md` 附錄提供了靜態資料的建議欄位與範例，可作為撰寫契約的起點，但在本節與 §7 補上之前，不視為已定義的契約。

### 6.1 酒款

預期需要表達：

- 識別碼與名稱。
- 類別（例如啤酒、烈酒、調酒）。
- 酒精濃度。
- 熱量換算所需的資料（建議為每 100 ml 熱量）。
- 隨機帶入時使用的預設杯數與預設容器。
- 資料來源。

### 6.2 容器

預期需要表達：

- 識別碼與名稱。
- 容量（ml）。fl oz 由前端換算顯示，不另外保存。

### 6.3 運動

預期需要表達：

- 識別碼與名稱。
- 運動換算所需的資料（建議為 MET 值）。
- 資料來源。
- 清單順序具有意義：即時換算顯示「第一個已開啟的運動」。

熱量單位固定為 kcal、容量固定為 ml；正式換算公式尚待確認（§8.1）。

## 7. API 契約詳細定義

每個 API 確認後，應使用以下格式補齊內容。

### API-01：酒款表

- Status: `Proposed`
- Method: `GET`
- Path: `/api/v1/drinks`
- Purpose: 取得所有可選擇的酒款，用於下拉選擇、文字篩選、隨機抽選與熱量計算。

#### Request

尚待確認是否需要查詢參數（目前篩選在前端進行）。

#### Response

尚待確認 JSON Schema。

#### Errors

尚待確認。可預見的失敗情境：讀取失敗、清單為空。

#### Notes

- 只能選擇本表中的酒款，不提供自訂（product-spec 需求 10）。
- 預設容器必須對應容器表中存在的容器。

---

### API-02：容器表

- Status: `Proposed`
- Method: `GET`
- Path: `/api/v1/containers`
- Purpose: 取得所有可選擇的容器與容量，用於容量選擇與熱量計算。

#### Request

尚待確認是否需要查詢參數。

#### Response

尚待確認 JSON Schema。

#### Errors

尚待確認。可預見的失敗情境：讀取失敗、清單為空。

#### Notes

- 選項以 ml 顯示並附註 fl oz（product-spec 需求 14）。

---

### API-03：運動表

- Status: `Proposed`
- Method: `GET`
- Path: `/api/v1/exercises`
- Purpose: 取得所有運動代償選項，用於設定面板的開關與運動換算。

#### Request

尚待確認是否需要查詢參數。

#### Response

尚待確認 JSON Schema。

#### Errors

尚待確認。可預見的失敗情境：讀取失敗、清單為空。

#### Notes

- 使用者的開關狀態不屬於本 API，保存在瀏覽器本地（§4.6）。
- 全部關閉時視同全部開啟（product-spec 需求 8）。
