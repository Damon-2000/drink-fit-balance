# Development Plan

## 1. 文件目的

本文件定義 醉後比較 的開發計畫，包含功能區塊、預定開發週次、交付成果、驗收標準及實際進度。

本文件供學生、講師及 AI Agent 在開發過程中共同使用，作為工作範圍、開發順序與完成狀態的依據。

### 1.1 相關文件

- `docs/spec/product-spec.md`：功能需求、業務規則與前後端及外部系統的職責分工。
- `docs/spec/development-plan.md`：開發規劃、工作區塊、週次安排與進度追蹤。
- `docs/architecture/api-contracts.md`：前端與後端的 API 契約。
- `docs/architecture/frontend-architecture.md`：前端技術選型、目錄結構、各層職責與 Mock 機制。
- `docs/wireframe/`：頁面配置與操作流程的視覺參考；適用範圍見 §2.4。
- `docs/guides/example-exercise-toggle.md`：範例模組說明。範例僅供參考與重置，不計入任何工作區塊的完成進度。

### 1.2 規劃原則

- 以 8 週作為預定開發週期。
- 以學生具備基本程式能力，並搭配 AI Agent 協作開發為前提。
- 開發過程須保留理解程式碼、除錯、整合與驗證的時間。
- 依功能相依性安排開發順序，不以單純完成畫面作為驗收標準。
- 優先建立可獨立開發的模組，並透過 Mock Data 或 Mock API 降低外部依賴。
- 每個工作區塊均須符合對應的驗收標準，才可標記為完成。
- 若實際進度與原定計畫有落差，應記錄原因與調整方式，不應直接覆蓋原始規劃。

## 2. 專案範圍

### 2.1 前端開發範圍

本專案前端需實作以下功能：

1. 整體頁面 Layout 與導覽。
2. API Client、資料型別與狀態管理。
3. 首頁、前一輪紀錄、身高體重與模式選擇。
4. 設定面板（運動代償開關、修改身高體重）。
5. 酒款輸入與選擇（篩選、隨機、沿用上一杯）。
6. 酒款資料設定與飲酒清單（杯數、容器、送出、刪除最後一杯）。
7. 醉後回本：即時運動換算與總結。
8. 醉後底線：血量設定與扣血。
9. 醉後底線：判定、成功與失敗報表。
10. 跨模組整合與例外處理。
11. CI/CD、部署與專案文件。

### 2.2 外部系統依賴

下列功能的實際執行不屬於單純的前端工作：

- 瀏覽器本地儲存（localStorage）：保存身高體重、運動開關、進行中的一輪與前一輪紀錄。本專案沒有後端，localStorage 即為使用者資料的唯一來源；資料可能被使用者清除或損毀，前端必須能處理讀不到或格式不符的情況。
- 靜態資料檔（酒款表、容器表、運動表）：由學生建立、講師審核，是熱量與運動換算的唯一依據。前端不得在元件中另外寫死熱量、容量或 MET 數值。

若後端或外部系統尚未完成，前端可先使用 Mock Data 開發，但必須清楚區分模擬結果與真實結果。

前端不得以瀏覽器計時器或輪詢機制，取代後端或外部系統負責的判斷。

### 2.3 預定交付成果

- 可正常執行的前端專案。

## 3. 進度追蹤規則

### 3.1 任務狀態

每個工作區塊使用以下狀態：

- `Not Started`：尚未開始。
- `In Progress`：實作或驗證進行中。
- `Blocked`：因外部依賴、規格不明或其他問題而無法繼續。
- `Done`：已完成實作，且驗收標準均已驗證。

不得只因程式碼已產生、畫面已呈現或 Agent 宣告完成，就將任務標記為 `Done`。

### 3.2 預定計畫與實際進度

本文件中的預定週次屬於原始規劃基準。

實際開發進度應記錄於各工作區塊的追蹤欄位，不應因任務延遲而直接修改原始預定週次。

若需要調整開發順序、範圍或時程，應說明調整原因與後續安排。

### 3.3 更新時機

- 開始工作時：更新狀態為 `In Progress`。
- 遇到阻塞時：更新狀態為 `Blocked`，並記錄原因。
- 完成實作時：更新已完成項目，但不代表已通過驗收。
- 完成驗證時：依 §3.5 記錄驗證方式與結果。
- 所有驗收條件均通過後：才可更新為 `Done`。

### 3.4 追蹤欄位

每個工作區塊應維護：

- Status：目前狀態。
- Completed Items：實際完成項目。
- Verification Notes：驗證方式與結果（依 §3.5）。
- Blockers：尚未解決的問題。
- Plan Changes：必要的範圍或時程調整。

不需要記錄每一次與 AI Agent 的對話，也不需要建立逐日工作日誌。

### 3.5 驗證方式

本專案不使用自動化測試框架。「驗證」只包含以下兩類，文件中提到的驗證或驗收結果均依此執行：

**靜態檢查（必須全部通過）：**

| 項目     | 指令                | 目的                         |
| -------- | ------------------- | ---------------------------- |
| 型別檢查 | `npm run typecheck` | 確認型別與契約、Mock 資料一致 |
| Lint     | `npm run lint`      | 確認程式碼符合專案規則       |
| 正式建置 | `npm run build`     | 確認專案可以完成正式建置     |

**功能驗證（手動）：**

1. 以 `npm run dev` 啟動專案。
2. 逐條對照該工作區塊的驗收標準，在瀏覽器中實際操作確認。
3. 需要失敗、逾時、空資料等情境時，依 `frontend-architecture.md` §6.2 手動切換 Mock 資料重現。
4. 在 Verification Notes 中，逐條記錄驗收標準的結果（通過、未通過或無法驗證）及使用的 Mock 情境。

**不屬於本專案的驗證方式：**

- 不安裝或撰寫單元測試、整合測試、E2E 測試。
- 不以「靜態檢查通過」取代功能驗證。
- 以 Mock 資料完成的功能驗證，只代表前端行為符合預期，不代表已與真實後端或外部系統整合。

### FE-03：首頁與模式選擇（Home & Mode Selection）

**預定週次：** Week 2

**功能範圍：**

- 首頁：無前一輪紀錄時顯示產品名稱、標語與「開始」；有前一輪紀錄時顯示摘要與「重新開始」（需求 1–3）。
- 重新開始的清除確認（需求 3）。
- 首次使用的身高體重輸入與範圍檢查（需求 4、5）。
- 模式選擇：醉後回本、醉後底線（需求 6）。
- 開啟網頁時若有進行中的一輪，直接回到該輪（需求 19a）。

**相依項目：** FE-01、FE-02。

**交付成果：**

- 首頁、身高體重輸入頁、模式選擇頁。
- 使用者資料與一輪紀錄的 localStorage 保存。

**驗收標準：**

- 清除 localStorage 後開啟首頁，顯示「開始」；按下後進入身高體重輸入，送出後進入模式選擇。
- 身高或體重空白、低於下限或高於上限時，送出按鈕不可用，欄位旁顯示原因。
- 已設定身高體重後重新整理，按「開始」直接進入模式選擇。
- 有前一輪紀錄時首頁顯示摘要；按「重新開始」出現清除提示，取消後紀錄仍在，確認後紀錄清除並進入下一步。
- 選擇模式並登記一筆後重新整理，直接回到進行中的這一輪，登記內容不變。
- 手動把 localStorage 中的資料改成不合法的格式後重新整理，畫面不會當掉，視為沒有資料。

**進度追蹤：**

- Status: `Not Started`
- Completed Items: 無
- Verification Notes: 尚未驗證
- Blockers: 無

**進度追蹤：**

## 6. AI Agent 協作規範

### 6.1 開始任務前

AI Agent 應：

1. 閱讀 `AGENTS.md`。
2. 閱讀 `product-spec.md` 中與任務相關的需求。
3. 確認對應的工作區塊、預定範圍及驗收標準。
4. 檢查相關程式碼、API 契約、`frontend-architecture.md` 及既有實作。
5. 對於未定義的行為，先列出問題，不自行假設重要的業務規則。

### 6.2 開發過程

- 優先完成範圍明確、可獨立驗收的小任務。
- 避免未經確認就擴大實作範圍。
- 不得將 Mock API 或模擬狀態描述為後端或外部系統已具備的能力。
- 若發現規格矛盾或 API 缺漏，應記錄問題與影響。
- 需要調整既有架構或開發順序時，應說明原因。

### 6.3 任務完成後

AI Agent 應：

1. 對照驗收標準檢查實作。
2. 依 §3.5 執行靜態檢查與功能驗證。
3. 說明實際完成的內容及驗證結果。
4. 更新本文件的實際進度欄位。
5. 若 API 契約有變動，同步更新 `api-contracts.md`。
6. 列出尚未完成的驗收項目與阻塞問題。

不得因程式碼已生成或建置成功，就直接將所有驗收項目標記為通過。

## 8. 風險與時程調整

### 8.1 主要風險

- 靜態資料（酒款表、容器表、運動表）與換算公式的正式內容延遲提供。
- localStorage 的資料格式在開發中變動，造成舊資料無法讀取。
- 學生需要額外時間理解 AI Agent 產生的程式碼。
- 進行中一輪的保存、重新整理還原與畫面狀態同步的複雜度高於預期。
- 部署環境或權限設定造成額外工作。

### 8.2 處理原則

- 正式靜態資料未就緒時，先使用 `product-spec.md` 附錄的範例資料推進前端工作。
- 對於未確認的 API，明確記錄提案與待確認事項。
- 優先確保核心操作流程與安全狀態提示正確。
- 若時程不足，優先調整非核心功能的完成範圍，不省略安全相關的規格驗證。
- 時程調整須記錄原因、受影響項目與新的預計完成時間。

### 8.3 8 週計畫的定位

8 週是預定開發目標，不代表所有功能一定能在期限內完成。

若實際進度落後，應根據剩餘時間、功能重要性、相依關係與驗收風險重新安排工作，並保留尚未完成的項目，不得以降低驗收標準的方式宣告完成。
